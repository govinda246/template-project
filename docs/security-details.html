まず、全体像をつかむ

この環境は「ゲームを作る部屋」と「外との出入口を管理する門番」の2つが中心です。 ブラウザーはlocalhostの3000番へ入り、門番を通ってゲーム画面に届きます。

2つのコンテナの役割

同じDockerイメージから作られていますが、仕事は分けられています。

開発担当

devcontainer

  • VS Codeが接続する作業場所
  • TypeScriptとPhaserでゲームを編集
  • Viteが3000番でゲームを配信
  • プロジェクトを /workspaces/github_agent_test に共有
  • 通常ユーザー node で動作
通信担当

egress-proxy

  • PCの3000番からdevcontainerのViteへ中継
  • 外向き通信のホスト名を検査
  • HTTPSの443番だけを許可
  • 許可対象は egress-allowlist.txt で管理
  • 読み取り専用のコンテナとして動作

通信はどう流れる？

ゲーム表示と外部通信では、流れが少し異なります。

A. ゲームを見る
  1. ブラウザーがlocalhostへアクセス

    http://127.0.0.1:3000 を開きます。

  2. egress-proxyの3000番が受け取る

    PCから見える入口はプロキシだけです。

  3. devcontainerのViteへ中継

    sandbox ネットワーク内の3000番へ送ります。

B. npmなどへ接続する
  1. devcontainerから通信を開始

    プロキシ設定により直接外へ出ません。

  2. 名前とポートをチェック

    許可リストの完全一致か、443番かを確認します。

  3. 許可された場合だけ中継

    データの中身は復号せず、HTTPSのトンネルを開きます。

大切な点: devcontainerは sandbox という内部ネットワークだけに接続します。 外部側の egress へ接続できるのはegress-proxyだけです。

守りは一重ではなく、多重になっている

1つが破られても、別の層が被害を小さくする設計です。

隔壁 1：Dockerネットワーク

sandbox と egress を分離

devcontainerは外部へ直接通じない内部ネットワーク sandbox だけに入ります。egress-proxyだけが sandbox と外部側の egress の両方へ入り、 2つの区画のあいだで許可された通信を中継します。

隔壁 2：Bubblewrap

コンテナの中もさらに小さな部屋に分ける

開発コマンドごとにPID、IPC、UTS、user namespaceを分離します。 ネットワークを完全に切る --offline も使え、ホームやシステム領域も 「見える範囲」「書き込める範囲」を限定しています。

「sandboxの隔壁」とは何か: devcontainer内で動くゲームやコマンドから、直接PCやインターネットへ自由に出られないよう、 ネットワーク、Docker権限、ファイルシステム、プロセスの4方向に境界を置くことです。 egress-proxyという限定された通路を通る通信だけが外へ進めます。
① 外向き通信 sandbox には外への経路がなく、許可済みHTTPS先だけをプロキシが中継
② Docker権限 root権限・追加capability・Docker socket・特権モードを与えず、ホスト操作を遮断
③ プロセス空間 BubblewrapでPID、IPC、UTS、user namespaceを分離し、別の作業を覗けない範囲を作成
④ ファイル空間 重要設定を読み取り専用にし、信頼スクリプトをroot所有の /opt/secure-template に配置

書き込みできる場所

主にゲームのソースコード。src などの通常作業フォルダーです。

読み取り専用の場所

.git、.devcontainer、.github、.vscode、scripts。

使えない危険な操作

docker、sudo、mount、Copilot CLIの直接起動など。

安全性のためにできないことと、その正当性

制限には「主要防御」「条件付きで必要」「補助的な事故防止」の違いがあります。 補助策は完全な防御ではなく、各制限の役割と位置づけを区別します。

できないこと 安全上の理由 防御区分 代替・注意点
許可リスト外のサイト・APIへ自由に接続 ソースコードや資格情報の持ち出しと、悪意ある実行ファイルの取得を減らします。 平文HTTPや443番以外も中継しません。 主要防御 必要なホストを完全一致で確認して egress-allowlist.txt に追加します。
PC・LAN内の別サービスへ直接接続 コンテナからホストや家庭内・会社内機器を探索・操作されないようにします。 localhost:3000 は公開されたゲーム入口に限られます。 主要防御 連携が必要なら、必要なAPIだけを明示的な窓口として設計します。
Docker、sudo、mount、nsenterなどの管理操作 Docker socketはマウントせず、全capabilityを外し、特権モードも使いません。 これを変えるとコンテナ隔離そのものが弱くなります。 主要防御 管理操作はコンテナ外で人が実行します。名前による拒否は補助策です。
SSH接続・SSH経由のGit push SSHは22番などの未許可ポートで接続でき、ホスト鍵や外部秘密鍵も渡されません。 任意サーバーを新しい通信経路にしないためです。 主要防御 pushや管理はホスト側で確認して行います。
GitHubやクラウドの資格情報を自動利用 侵害された依存関係や実行コマンドが、リポジトリやクラウドへ認証済み操作を行うことを防ぎます。 主要防御 必要なときだけホスト側で認証し、短命なトークンを使います。
.git、設定、scriptsを安全シェルから書き換え エージェントが自身の制限、CI、信頼スクリプトを同じ実行中に書き換える経路を防ぎます。 主要防御 人が差分をレビューし、変更後にDev Containers: Rebuild Containerで再確認します。
Copilot CLIの直接起動や自動承認された端末操作 監督のない入れ子実行と、レビュー前の危険な操作を減らします。 ただしコマンド名検査は回避可能なので主要防御ではありません。 補助防御 VS Codeの手動承認付きAgent、ネットワーク分離、資格情報非継承が本体の防御です。
npm依存関係や取得したスクリプトを完全に信頼しない 許可リストは通信先を絞るだけで、npmパッケージやGitHub上のコード自体が安全とは保証しません。 依存関係スクリプトは通常コマンド権限で動きます。 別途対策 lockfile、バージョン固定、差分レビュー、npmスクリプト確認、必要なら npm ci --ignore-scripts を使います。
設計上の位置づけ: 主要な制限は、セキュリティ上の目的と実際の防御に対応しています。 一方、特定コマンド名を弾く方式は事故防止の補助策であり、完全な防御ではありません。 また、許可したGitHubやnpmのホスト名から流れるコードは安全性を保証されないため、 通信制限だけでなく依存関係のレビューが必要です。

利便性のために制限を緩める方法

いきなり全制限を解除するのではなく、目的ごとに最小限だけ緩めます。 特に「許可した通信先」と「与えた資格情報」は別々に管理します。

段階1・低

ホストを追加

必要なAPIを完全一致で1件ずつ許可します。最も狭い緩和です。

段階2・中

承認を増やす

特定操作だけ自動承認します。資格情報は渡さないままにします。

段階3・高

資格情報を渡す

短命トークンや限定権限だけに絞り、利用後に削除します。

段階4・重大

Docker・ホストへ接続

コンテナ隔離を越えます。別環境で人が明示実行する方が安全です。

目的 最小限の緩め方 増える利便性 主なリスク リスク
特定APIや追加パッケージを使う 完全なホスト名と必要性を確認し、 egress-allowlist.txt に追加してプロキシを再起動。 ワイルドカードやIPの無制限許可は避ける。 npm package、公式API、固定CDNを利用できる 許可ホストから悪意あるコードやデータを受け取る可能性。 大きなGitHub/npm配信網は「ホスト単位」では内容保証にならない。 要レビュー
PC上の開発サーバーやDBと連携 host/ポート単位の専用プロキシを設け、必要なAPIだけ転送する。 host networkや全ポート公開は行わない。 ローカルDB、画像生成、モックAPIなどと連携できる LAN探索、管理画面や認証済みローカルサービスへの不正アクセス。 用途限定
GitHub pushを容器内でも使う 標準手順ではホスト側pushを使用。必要な場合は期限・対象リポジトリ・権限を限定した fine-grained tokenを一時的に渡す。 長期的な個人トークンやSSH秘密鍵は渡さない。 Agentからのコミット後すぐ公開できる 侵害されたコードが権限内のリポジトリを書き換えられる。 高リスク
反復作業を自動承認する chat.tools.terminal.autoApprove は読み取り専用コマンドや テストなど、完全一致のコマンドだけに限定する。 ワイルドカードや任意シェル実行を許可しない。 確認回数を減らし、定型テストや差分確認を速くできる 自動承認範囲が広すぎると、見せかけた同名操作やコマンド連結を通す可能性。 破壊的操作は常に手動承認。 限定的
Agentに設定ファイルを編集させる 変更対象を.vscodeなど1種類に限定し、 .git・信頼スクリプト・セキュリティ設定は読み取り専用のままにする。 開発ツール設定の更新が楽になる セキュリティガードレールやCIを実行主体が直接弱められる。 高リスク
コンテナからDockerを使う 原則として行わず、ホスト側の承認付きスクリプトや別管理マシンを使う。 Docker socketのマウントやprivilegedはこの環境では推奨しない。 テスト用コンテナや複合サービスをAgentから起動できる Docker socket利用者は実質的にホスト管理者。ファイル読み出し、 コンテナ作成、マウントによる資格情報窃取が可能。 非推奨
安全な緩和の順番
  1. 必要な目的と期限を決める
  2. 許可する対象を1つだけ追加する
  3. コード・設定差分を人がレビューする
  4. 再ビルドしてセキュリティテストを実行する
  5. 不要になった許可・秘密を削除する
同時に緩めないもの
  • 外部ネットワークと長期資格情報
  • Docker socketと保護ファイルへの書き込み
  • host networkと自動承認
  • 任意コード実行とクラウド管理権限

同時に緩めると、侵害時に被害がホストや外部サービスへ直結します。

緩和方針: 「できることを増やす」より「今回必要な1機能だけを期限付きで許可する」方が安全です。 緩和後もネットワーク、資格情報、ファイル、Docker権限は別々に見直し、 1つを緩めても他の層は変更しません。

この環境でも防御できない、または保証できない問題

サンドボックスは被害の入口と範囲を狭めますが、完全な安全を保証するものではありません。 以下は、設定しても残る重要なリスクです。

残る問題 なぜ防ぎ切れないか 期待できること 追加で必要な対策
許可済みホストからの悪意あるコード GitHub、npm registry、許可APIは通信先を識別するだけで、 パッケージやリポジトリの内容を信頼できると判断していません。 通信先を固定し、未知の外向き接続や資格情報への接続を制限できる lockfile固定、署名・出所確認、依存関係差分、lifecycle script確認、SBOM・脆弱性監査
許可範囲内へのデータ送信 許可したGitHubやAPIへのHTTPSは復号せず中継します。 正規に見える接続の中身まで検査する設計ではありません。 許可していないドメインへの直接送信を減らせる 秘密を置かない、送信データ最小化、プロキシログやサービス監査ログ、外部のDLP
Linuxカーネル・Docker・Bubblewrapの未知の脆弱性 これらは共通のカーネルと実行基盤に依存するため、 コンテナ脱出や権限昇格の脆弱性をこの設定だけで消すことはできません。 権限削除と多層化により、脆弱性を利用しにくくし被害を限定できる ホストOS・Docker・カーネル・イメージの更新、再現テスト、重要作業は専用VM
プロジェクト領域内のファイル破壊・改ざん ゲーム開発のため、srcなど多くのプロジェクトファイルには書き込み権限があります。 .gitや設定ファイルの一部は読み取り専用にできる Git差分、バックアップ、遠隔コピー、重要ファイルの権限分離、未コミット作業の回収手順
資源枯渇と書き込み領域の使い切り ComposeにCPU・メモリ・PID上限とログローテーションは設定済みですが、 Dockerボリュームやホストディスクの容量上限は設定していません。 悪意ある処理や大量の生成物がストレージを消費する可能性があります。 CPU・メモリ・PID・ログ増加を抑え、暴走の影響範囲を小さくできる ディスククォータ、Dockerストレージ監視、バックアップ、復旧手順
プロンプトインジェクションや人を騙す指示 文書・画面・依存関係の内容が信頼できるとは限らず、モデルや人に危険な操作を促す場合があります。 技術的制限だけでは意図や騙しを判定できません。 自動承認を切り、危険な権限・資格情報・通信先を分離できる 人による差分レビュー、操作前確認、外部コンテンツを指示として扱わないルール
ブラウザー・VS Code拡張・IDE自体の脆弱性 エディターや拡張機能は開発環境と統合され、独自の更新・権限モデルを持ちます。 ゲームコード用sandboxの外側で動く部分もあります。 拡張のバージョン固定、編集・端末の手動承認、不要な権限の無効化はできる 拡張の最小化、公式配布元確認、VS Code/ブラウザーの更新、拡張権限レビュー
ホストが既に侵害されている場合 Docker、ブラウザー、ファイルシステム、入力端末の土台であるホスト自体が安全とは限りません。 コンテナはホストからの攻撃を防ぐ境界ではありません。 ホストへ渡す権限を減らし、侵害時の対象範囲を小さくできる マルウェア対策、ホスト更新、ディスク暗号化、バックアップ、強い資格管理
公開GitHub Pagesやリポジトリからの情報漏えい GitHub Pagesは公開サイトで、リポジトリも現在Publicです。 コンテナ内の秘密があるとは限りませんが、一度コミットした情報は履歴に残り得ます。 資格情報を渡さず、公開対象をdocsへ絞る 公開前レビュー、secret scanning、コミット履歴確認、秘密発見時の直ちに失効・履歴整理
設定ミス・緩和の積み重ね Docker socket、host network、特権モード、広い自動承認、長期資格情報を後から追加すると、 本来の境界を上書きできます。 現在の設定では主要な緩和を無効にしている 変更ごとのレビュー、セキュリティテスト、期限付き例外、不要な権限の削除
この環境の前提: ホストOS、Docker、VS Code、実行イメージは信頼し、通常の開発者の誤操作と プロジェクト内コードの侵害を減らすことを主目的とします。 非常に危険なマルウェア解析、秘密情報を扱う作業、敵対的な本番管理には、 更新済みの専用VMやハードウェア隔離された管理端末が必要です。

より安全にするための方針

このプロジェクトでは、日常のゲーム開発に必要な利便性を保つため全てを採用していません。 ただし、重要な作業では次のより強い構成を選べます。

実装済みの追加対策
1
資源上限

CPU・メモリ・PID・ログ容量の上限をComposeへ設定済みです。

2
依存関係を自動検査

npm auditとDependabotを追加済みです。Secret scanning、Push protection、private vulnerability reportingもGitHub上で有効化済みです。SBOM生成は運用方針に応じて追加します。

3
Actions参照を固定

GitHub ActionsをコミットSHAで固定し、タグ内容の変更による供給網リスクを減らします。

4
ネットワークの一時無効化

外部通信不要のビルド・テストでは --offline を利用できます。

このプロジェクトでは採用していない、より強い方法
  • 開発ごとに使い捨ての専用VMを作り、作業後に破棄
  • 完全オフライン環境で事前承認済み依存関係だけを使用
  • 共有フォルダーではなく、読み取り専用コピーと成果物だけを受け渡し
  • 資格情報のない物理的・管理的に分離した端末で公開操作
  • ネットワーク、ファイル、プロセスのログを外部監視基盤へ送信
  • CIで署名済み成果物だけをデプロイし、内容・出所を検証

これらはより強い隔離を提供しますが、起動時間、操作手順、更新管理、 ハードウェア・運用コストが増えるため、通常のブラウザーゲーム開発には未採用です。

実際に起動する手順

VS Codeでこのリポジトリを開き、Dev Containerで再度開くのが基本です。

  1. Docker Desktopを起動

    Dockerが動いていないと、コンテナを作れません。

  2. VS Codeで「Reopen in Container」

    devcontainer.json と docker-compose.yml の設定を読み込みます。

  3. 依存関係を導入してゲームを起動 
    npm ci
npm run dev
  4. ブラウザーで確認

    http://127.0.0.1:3000 を開きます。

2つのコンテナ、ネットワーク、公開ポート、共有フォルダーを決めます。

.devcontainer/Dockerfile

Node.jsやBubblewrapを含むコンテナの設計図です。

.devcontainer/egress-proxy.mjs

外向きHTTPSとゲーム画面を中継するプロキシの実体です。

scripts/secure-run

Bubblewrapでコマンドの見える範囲を小さくして実行します。

package.json

Phaser、Vite、TypeScriptなどのアプリ部品と実行コマンドです。
